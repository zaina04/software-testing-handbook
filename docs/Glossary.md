# Software Testing Glossary

A quick reference for the most important software testing terms from the ISTQB Foundation Level syllabus.

---

## Acceptance Testing
Testing performed to determine whether the software meets business and user requirements before release.

## Agile
A software development approach that delivers software in small, iterative increments with continuous feedback.

## Black-Box Testing
Testing that evaluates software functionality without knowledge of its internal code.

## Boundary Value Analysis (BVA)
A test design technique that focuses on values at the edges of valid input ranges, where defects are most likely to occur.

## Branch Testing
A white-box testing technique that ensures every possible branch or decision outcome has been executed.

## Checklist-Based Testing
An experience-based testing technique that uses a predefined list of checks during testing.

## Configuration Management
The process of managing versions of software, test artefacts, and documentation to ensure consistency.

## Confirmation Testing
Testing performed after a defect has been fixed to verify that the fix works.

## Decision Table Testing
A black-box technique used when software behaviour depends on multiple conditions and their combinations.

## Defect (Bug)
A flaw in the software that may cause incorrect behaviour.

## Defect Clustering
The principle that a small number of modules often contain most of the defects.

## DevOps
A culture and set of practices that integrate development and operations to enable faster and more reliable software delivery.

## Dynamic Testing
Testing performed by executing the software.

## Entry Criteria
Conditions that must be satisfied before testing can begin.

## Equivalence Partitioning (EP)
A technique that divides input values into groups expected to behave similarly, reducing the number of test cases.

## Error (Mistake)
A human action that produces an incorrect result, potentially leading to a defect.

## Error Guessing
An experience-based technique where testers use intuition and past knowledge to predict likely defects.

## Exit Criteria
Conditions that must be met before testing is considered complete.

## Exploratory Testing
A testing approach where learning, test design, and execution happen simultaneously.

## Failure
A situation where the software behaves differently from the expected result during execution.

## Functional Testing
Testing that verifies the software performs its required functions correctly.

## Inspection
The most formal type of review, following a structured process to identify defects.

## Integration Testing
Testing that verifies interactions between different software components.

## Maintenance Testing
Testing performed after software changes or updates to ensure existing functionality still works.

## Non-Functional Testing
Testing that evaluates quality attributes such as performance, usability, security, and reliability.

## Quality Assurance (QA)
Activities focused on preventing defects by improving development and testing processes.

## Quality Control (QC)
Activities focused on identifying defects in the software product.

## Regression Testing
Testing performed to ensure recent changes have not introduced new defects into existing functionality.

## Review
A static testing activity where work products are examined without executing the software.

## Risk-Based Testing
A testing approach that prioritises testing based on the likelihood and impact of failures.

## Shift-Left Testing
Starting testing activities as early as possible in the software development lifecycle.

## Software Development Life Cycle (SDLC)
The structured process used to plan, develop, test, deploy, and maintain software.

## Software Testing
The process of evaluating software to verify that it meets requirements and behaves as expected.

## Statement Testing
A white-box testing technique that ensures every executable statement has been executed at least once.

## Static Analysis
The use of tools to examine source code without executing it.

## Static Testing
Testing performed without running the software, such as reviews and code analysis.

## State Transition Testing
A black-box technique that verifies software behaviour as it moves between different states.

## System Testing
Testing the complete integrated system against specified requirements.

## Test Case
A set of inputs, conditions, and expected results used to verify a specific feature or function.

## Test Coverage
A measure of how much of the software or its requirements have been tested.

## Test Data
The input values used during testing.

## Test Design
The process of creating effective test cases based on requirements and risks.

## Test Execution
Running test cases and comparing actual results with expected results.

## Test Level
A stage of testing with a specific objective, such as Unit, Integration, System, or Acceptance Testing.

## Test Plan
A document describing the objectives, scope, approach, resources, and schedule for testing.

## Test Process
The sequence of activities involved in planning, designing, executing, and completing testing.

## Testware
All artefacts produced during testing, including test plans, test cases, scripts, and reports.

## Traceability
The ability to link requirements to test cases and test results to ensure complete coverage.

## Unit Testing
Testing individual components or functions, usually performed by developers.

## Validation
Confirming that the software satisfies user and business needs.

## Verification
Checking that the software has been built according to its specifications.

## Walkthrough
A review led by the author to explain a work product and gather feedback.

## White-Box Testing
Testing that examines the internal structure, logic, and code of the software.
